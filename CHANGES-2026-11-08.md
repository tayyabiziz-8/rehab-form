# Review fixes — 8 Nov 2026

Changes made on top of the Keraal Group 3 evaluation. Nothing in the evaluation logic was rewritten; the fixes are targeted.

## Fixed

1. **BlazePose aspect ratio** — `src/rehabform/keraal.py::load_blazepose`
   - Keraal stores BlazePose x as a fraction of image width and y as a fraction of image height (Group 3: 960 × 544). Using these raw values squashes horizontal distances to ~57% of vertical ones, so diagonal angles are wrong (true 45° reads ~30°).
   - `load_blazepose` now returns **pixel units by default**: x × 960, y × 544, z × 960 (MediaPipe's z is on roughly the same scale as x). New argument `image_size=(w, h)`; pass `image_size=None` for raw values. **Groups 1a/1b/2a/2b videos are 480 × 360 — pass that size for them.**
   - Every existing script that calls `load_blazepose` picks this up automatically.

2. **BlazePose landmark order** — same function
   - Previously the landmark order came from the JSON key order and only the set of names was checked. Landmarks are now placed by **name** in the canonical order (`BLAZEPOSE_ORDER`, from the dataset readme). Missing landmarks become NaN instead of crashing.

3. **Shoulder diagnostic vertical axis** — `scripts/diagnose_shoulder_angles.py`
   - `candidate_angles` used image "up" (−y) for Kinect too. Kinect's y points up, so its vertical reference was upside down and the "vertical 3D" candidate was penalised unfairly. New argument `vertical_positive_up` (False for BlazePose, True for Kinect).

## Added

4. **Offset-free Vicon evaluation** — `scripts/evaluate_keraal_vicon_offsetfree.py`
   - Compares BlazePose (2D and 3D variants) with Vicon using **change from the start pose** and **range of motion**, which cancel the fixed offset from ART targets sitting on segments.
   - Vicon angles use segment directions (shoulder→arm target, forearm→hand target, hips→chest), not targets as joints.
   - Resamples Vicon to video time, searches ±1 s lag, flips sign for signed angles if needed; reports r, change-from-start MAE and ROM error, by exercise and by participant.
   - Outputs: `outputs/keraal_vicon_offsetfree_per_recording.csv`, `outputs/keraal_vicon_offsetfree_summary.csv`.

5. **Tests** — `tests/make_synthetic_keraal.py`, `tests/test_keraal.py`
   - Synthetic Keraal folder (all five modalities, JSON keys in reversed order, known arm motion).
   - Tests: landmarks ordered by name; pixel conversion restores a 45° angle that raw values squash to ~30°; BlazePose and Kinect give the same vertical-reference shoulder angle.
   - All existing evaluation scripts were run on the synthetic folder after the change and complete without errors.
   - Side finding: on this synthetic data, where phone and Vicon agree exactly, `compare_keraal.py` still reports ~21° shoulder-abduction error — the fixed offset from the single Hips target and segment-mounted targets.

6. **Docs** — warning box at the top of `docs/Keraal Group 3 - Initial Angle Evaluation.md`; README table updated.

# Follow-up diagnostics — after the corrected rerun

The rerun showed ELK arm elevation moving opposite to Vicon (median r = -0.52) in every recording. Two tools to find out why:

1. **Signed frontal-plane arm angle** — `evaluate_keraal_vicon_offsetfree.py` now also reports `arm_abd_signed_l/r` (BlazePose 2D vs Vicon): 0 = arm down, 90 = sideways, 180 = overhead, beyond 180 = past overhead, negative = across the body. Both systems use the same references (trunk midline and shoulder line), the angle is unwrapped over time, and **no sign flip is applied**, so a negative r means genuinely opposite motion. Tests whether the failure is the unsigned angle folding back near 180 degrees (`tests/test_keraal.py` now proves the signed angle keeps rising past 180 while the unsigned one folds).
2. **Length check** — recordings whose Vicon/video lengths imply a Vicon rate outside 15–30 Hz are skipped with a message (real Group 3 Vicon is ~19.5 Hz; this drops `G3-CTK-P2T3-Unknown-E3B3-0`).
3. **Overlay** — `scripts/overlay_blazepose.py` saves `outputs/overlays/overlay_<recording>.png`: 4 frames (start, Vicon left-arm peak, Vicon right-arm peak, largest left-arm disagreement) with the BlazePose skeleton drawn (left orange, right blue, wrists labelled L/R) and phone vs Vicon signed arm angles printed on each frame. It also prints which image side BlazePose's "Left" shoulder is on.
4. **Synthetic data** now uses 20 Hz Vicon (like the real data), can raise the arm past 90 degrees, and can write a small stick-figure video for testing the overlay.

# Root cause found: the shipped BlazePose is mirrored (14 Nov 2026)

**Evidence.** The overlays show the BlazePose skeleton mirrored about the image centre (drawn to the right of the person when the person sits left of centre). In the flank stretch (ELK), BlazePose's left arm tracks Vicon's right arm: at the peak frames of all three participants, the mean gap is 149 degrees same-side but 23 degrees with sides swapped. The signed arm angle stayed negative in ELK (r about -0.6), which rules out the "fold near 180 degrees" explanation. This also explains the 72-85 degree ELK shoulder disagreement with Kinect: the ELK arm movement is one-sided, so swapped labels show up there, while symmetric exercises (CTK, RTK) hide them.

**Fix** — `src/rehabform/keraal.py`:
- New constant `KERAAL_BLAZEPOSE_MIRRORED = True`; `load_blazepose(..., unmirror=True)` by default replaces x with 1 - x and swaps every `Left_`/`Right_` landmark. Pass `unmirror=False` for the file as shipped. Checked for Group 3 only; check Groups 1a/2a with the overlay before relying on it there.

**Also changed**
- Signed frontal-plane arm angle: frames where the arm points towards or away from the camera (in-plane length below 50% of its full length) are now left out. In CTK (arms raised forwards) this projection is meaningless and previously produced spurious 360-degree jumps in 39% of recordings.
- Synthetic test data is now written mirrored, exactly like the real files, and `tests/test_keraal.py` has a test that un-mirroring restores the person's true left arm.

# Vicon joint angles from segment orientations (14 Nov 2026)

**Why.** After un-mirroring, sideways arm movement tracks Vicon in time almost perfectly (r ~0.99), but the phone's range of motion is 30-40 degrees larger. Either the phone overstates or the target-position Vicon angle understates (e.g. the "shoulder" target moving with the arm).

**Added**
- `src/rehabform/keraal.py::load_vicon` — full rows `(frames, 17, 7)` including the orientation quaternion (x, y, z, w).
- `scripts/evaluate_vicon_quaternions.py` — joint rotation between segments from their orientations, needing no knowledge of how targets were mounted: relative orientation child-vs-parent, change from the start pose, rotation vector; the joint's main axis is the principal direction of those vectors. Joints: chest→upper arm (bypasses the shoulder target), upper arm→forearm (elbow), hips→chest (trunk). Reports per exercise: ROM from phone, from target positions and from quaternions; how well phone and target angles follow the quaternion angle; `axis_share` (1.0 = pure single-axis movement).
- Synthetic Vicon now has real orientation quaternions with random per-target mounting; new test shows the angle is recovered exactly regardless of mounting.

**How to read the output**
- `ROM target` < `ROM quat` and `r target~quat` high → target-based angles understate; phone ROM should then sit closer to `ROM quat`.
- `ROM phone` > `ROM quat` as well → the phone overstates.
- Low `axis_share` → the joint rotates about several axes at once (e.g. arm rotation along its own axis), so a single-angle comparison is less meaningful.

```bash
python tests/test_keraal.py
python scripts/evaluate_vicon_quaternions.py --root data/keraal --limit 5
python scripts/evaluate_vicon_quaternions.py --root data/keraal
```

# Arm-angle trunk reference diagnostic (15 Nov 2026)

**Why.** Against orientation-based Vicon (chest → upper arm), phone arm ranges match within ~5° in CTK and RTK but read 45–56° too large for overhead sideways reach (ELK), with near-perfect timing. The phone measures the arm against the hip-to-shoulder midline; Vicon against the chest. During a flank stretch the trunk also bends sideways.

**Added** `scripts/diagnose_arm_reference.py`: the phone's signed arm angle against four references, each compared with Vicon:
- `midline` — current metric (mid-shoulder → mid-hip, image plane)
- `shoulder_perp` — perpendicular to the shoulder line (chest-like, follows the upper trunk)
- `vertical` — image vertical (ignores the trunk)
- `midline_3d` — midline in 3D with BlazePose depth (tests whether image projection inflates the angle)

Checked on synthetic data, plus a tilted-torso check (30° tilt: trunk references read 0°, vertical reads −30°).

**Reading the result:** the reference whose `diff` (phone ROM − Vicon ROM) is closest to 0 in ELK, without hurting CTK/RTK, becomes the app's arm metric. If none closes the gap, the cause is elsewhere (likely BlazePose's shoulder point rising when the arm is overhead).

```bash
python scripts/diagnose_arm_reference.py --root data/keraal --limit 5
python scripts/diagnose_arm_reference.py --root data/keraal
```

# Angle spec and trust table (16 Nov 2026)

Turns the Pillar 1 findings into code the app and the findings engine share.

- `src/rehabform/angles.py` — the four measures, computed exactly as validated (pixel units, un-mirrored, image y down): `arm_elevation` (signed, against the shoulder-line perpendicular — the reference chosen on 15 Nov), `elbow_flexion` (image plane), `trunk_lean` (tilt from vertical, + = towards the person's left), `trunk_rotation` (BlazePose depth; timing only). Each returns `(values, valid)`; `valid` is False when a limb points towards the camera (image length < 50% of its reference length). For live use pass the calibrated limb length instead of relying on the recording's 90th percentile.
- `config/trust_table.json` — version 3: per measure and exercise, a mode (`range`, `relative`, `timing_only`, `not_reportable`), a clinician-facing note, and the evidence numbers; an overhead rule (arm above 110° → relative); exercise descriptions; Keraal's nine errors mapped to measures with thresholds left empty (to calibrate on Groups 1A/2A). Two CTK errors have no validated measure yet (flagged as `gap`).
- `TrustTable.decide(measure, exercise, value)` returns the mode, note and evidence.
- `tests/test_angles.py` — known poses (0/45/90/135° arm, 90° elbow, 30° lean), trunk lean does not leak into the arm angle, foreshortened arm is invalid, `arm_elevation` matches the validated `shoulder_perp` metric exactly, and the trust-table decisions.
